# Product Case Methodology Iteration Memory

This file stores user-aligned decomposition preferences. Update it when the user explicitly corrects the framework, says “以后要…”, “这个要写进 SOP”, “对齐 SOP”, or provides a better decomposition principle.

## Current user-aligned standards

1. Do not only summarize product history; explain **what the product did to succeed**.
2. Always answer: **what it did, why it succeeded, what it captured versus competitors, how it developed after 0-1, what problems appeared, and how it solved them**.
3. If there are competitors/substitutes, prioritize **competitor gap + break-through path**.
4. If competitors/substitutes exist, do not write a “no obvious competitor” branch. Instead dissect the 0-1 product construction path: market demand → customer task → core bottleneck → old-solution gap → product scheme → MVP/landing loop. Only use opportunity discovery path when no competitors/substitutes truly exist.
5. The key output is not “success story” but **mechanism**: old assumption/cost structure → new insight → product/operation mechanism → proof → flywheel → risk.
6. For full product cases, continue beyond 0-1 into **1-10/10-100 development**, including growth-stage problems and solutions.
7. The skill should be iterative: when the user gives new decomposition feedback, update this memory and the relevant skill reference files so future cases improve. The skill, not the Obsidian SOP, is the source of truth.
8. High-value wedge problems should be evaluated by four dimensions: pain intensity, cost of inaction, defensible difficulty, and willingness to pay, divided by adoption friction. Use behavior evidence, not just verbal interest.
9. When asked “why this company can but others cannot,” analyze point capability vs system capability, input sale vs outcome responsibility, one-off project vs workflow embedding, generic supply vs managed supply network, and vertical dependency vs capability migration.
10. Product transformation should be analyzed as customer bottleneck migration + old-business commoditization + transferable core capabilities + value-chain movement + choice/result/new-risk table. Do not describe transformation as simply chasing a new trend.
11. After a processed article/case is done, factual correctness and misleading-risk review is a separate high-reuse skill: `$note-accuracy-auditor`. It outputs a chat-only report by default and should not be embedded in the article.

12. For product cases with clear adjacent competitors, include a **named competitor differentiation matrix**, not only generic substitute categories. Compare by customer JTBD, value-chain control point, product form, supply/quality mechanism, workflow depth, moat, risk, and PM memory label. Example pattern: Scale AI vs Surge AI vs Labelbox vs Encord.
13. For platform/infrastructure cases, add a **real early-platform pain** section: what was hard in building the first workflow, not just market positioning. Decompose task definition, workflow splitting, supply organization, quality control, cost/efficiency tradeoff, outcome proof, customer trust, and repeatable productization.

## Update protocol

When user feedback changes the desired decomposition method:

1. Identify the new principle in one sentence.
2. Decide where it belongs inside the skill:
   - Core trigger/workflow → `SKILL.md`
   - Detailed framework/checklist → `references/product-case-frameworks.md` or `references/independent-case-sop.md`
   - Output wording/template → `references/templates.md`
   - User preference/evolution → this file
3. Patch the smallest necessary skill files; do not rewrite unrelated content.
4. Only update an Obsidian SOP/note if the user explicitly asks to document or mirror the skill there.
5. In the final response, mention the changed skill files and the new rule in one sentence.
